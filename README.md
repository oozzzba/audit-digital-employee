# 审计数字员工（Audit AI Agent）

面向审计人员的 AI 流程执行助手：输入一个审计任务，自动跑完 **六阶段审计全生命周期闭环**，
并在每个高风险节点交给**人工闸门**确认放行。核心原则：**AI 出草稿、人放行**——审计是强合规场景，绝不代劳终审与销号。

## 定位

不是聊天机器人，而是一个**流程执行应用**：
理解任务 → 检索制度(RAG) → 取数筛查异常 → 风险判断 → 生成底稿/报告/整改台账 → 归档，
每一步都基于真实数据与知识库，可溯源、防幻觉，高风险环节人确认。

## 六阶段闭环

```
调度中心 Orchestrator（任务解析 + 阶段路由 + 人工闸门 + 前置条件校验）
  ├─ ① 立项申请     initiation     审计对象/范围/类型/目标/期间 → 立项申请
  ├─ ② 审前准备     preaudit       审计实施方案（9 章模板）
  ├─ ③ 现场实施     field          取数筛查异常 + 法规检索 + 风险判断 + 工作底稿
  ├─ ④ 报告编制     report         审计报告初稿（按审计类型套不同模板）
  ├─ ⑤ 整改督办     rectification  整改台账 + 督办建议（销号须人工确认）
  └─ ⑥ 项目归档     archive        归档清单（缺失标「待补充」，入库须人工核验）
```

每两个阶段之间一道 **【人工闸门】**：本阶段产出为草稿，确认通过后才进入下一阶段。

### 前置条件链（审计实务强约束）

进入每个阶段前，调度中心会校验「前置条件」是否满足，不满足则拦截并列出尚缺项：

| 阶段 | 前置条件 |
|------|----------|
| 立项 | 年度审计计划已审批、项目负责人已任命 |
| 审前准备 | 立项审批通过 |
| 现场实施 | 审计实施方案已审批、审计通知书已送达、审计资料已收集 |
| 报告编制 | 现场实施完成、问题已定性确认 |
| 整改督办 | 审计报告已发布 |
| 项目归档 | 整改闭环完成（或项目终止） |

用户说「审计 / 继续 / 下一步 / 确认 / 通过」时，系统按当前所处状态推进并确认闸门；乱序请求（如没立项就要报告）会被拦截。

### 审计类型 → 报告模板（四大类）

| 审计类型 | 报告模板 | 章节 |
|----------|----------|------|
| 经济责任审计 | 17.1 | 七章（基本情况 / 履职评价 / 问题与责任认定 / 审计意见 / 整改复审 / 其他事项 / 建议） |
| 竣工决算审计 | 17.2 | 七章（项目基本情况 / 投资完成与资产交付 / 管理评价 / 问题及处理意见 / 整改复审 / 其他事项 / 建议） |
| 在建跟踪审计 | 17.3 | 六章（项目基本情况 / 问题及处理意见 / 立行立改成效 / 整改复审 / 其他事项 / 建议） |
| 其他（通用） | 17.4 | 六章（基本情况 / 审计评价 / 问题及处理意见 / 整改复审 / 其他事项 / 建议） |

任务解析会输出「审计类型」字段，报告编制阶段据此路由到对应模板。

## 技术架构

```
app.py             Web 服务层（FastAPI + uvicorn，会话隔离）
  ├─ orchestrator.py  调度中心：任务解析 + 阶段路由 + 人工闸门
  ├─ agents.py        六阶段 Agent（各自 Prompt + 产出模板）
  ├─ generator.py     DeepSeek API 封装（deepseek-chat，temperature 0.3）
  ├─ retriever.py     BM25 检索（jieba 分词 + rank-bm25，按阶段收窄范围）
  ├─ data_tool.py     现场取数筛查（差旅费 / 物资采购 数据源 + 规则）
  ├─ ledger_data.py   历史整改台账（真实数据，脱敏，2899 条）
  ├─ problem_data.py  审计问题库（真实数据，脱敏，6096 条）
  ├─ knowledge/       9 篇知识文档（法规 + 制度 + 模板 + 定性标准 + 案例）
  ├─ scripts/         脱敏脚本（原始 xlsx → 脱敏 csv）
  └─ static/          前端（工作台 + 6 个结果页）

main.py             命令行入口（同一套 orchestrator/agents/generator）
```

## 快速开始

```bash

# 2. 配置 DeepSeek Key（在 .env 里填入，勿提交到 git）

# 3. 运行（二选一）
```

## 部署

### 容器化（目标机一键部署）

已提供完整容器化配置，任何装有 Docker 的机器（macOS 13+ 配 Docker Desktop，或任意 Linux）一条命令拉起：

```bash
cd code
docker compose up -d --build
```

- 镜像 `python:3.11-slim`、单 worker；DeepSeek Key 由 `.env` 运行时注入，**不进镜像**（`.dockerignore` 已排除 `.env`）。
- SQLite 落到命名卷 `audit_data`（容器内 `/data/audit.db`），容器重建/升级**不丢项目状态**。
- 内置 healthcheck：`GET /health` 返回 `{"status":"ok","db":...}`，`restart: unless-stopped` 异常自动拉起。

### 本机说明（开发机，诚实记录）

本开发机为 **macOS 12（已 EOL）**：无 Docker Desktop，colima 依赖 qemu 而 qemu 无法在本机构建（Homebrew 已明确「不支持此旧版本」）。因此容器化配置**已通过 `docker compose config -q` 语法校验，但未在本机实跑**——本机演示直接用上面的原生方式跑 `python3 app.py` 即可。容器化是「目标机部署产物」，不是「本机演示前置条件」。

### 持久化

`db.py` 用标准库 `sqlite3` 落盘（`audit.db`，`AUDIT_DB_PATH` 环境变量可覆盖路径），存项目状态 / 阶段产出 / 会话 / 聊天记录，**服务重启不丢进度**；前端用 localStorage 记住 `session_id`，刷新页面会话不丢。`GET /api/chat` 回放历史会话，`/health` 暴露持久化项目数。

## 真实数据（脱敏）

原型的两块「结果数据」均来自国家管网审计管理信息系统，经脱敏脚本处理后落盘，**不是编造的 demo 数据**：

| 结果页 | 数据源 | 规模 | 脱敏方式 |
|--------|--------|------|----------|
| 历史整改台账 | 审计问题整改台账 | 2899 条 | 单位/人名 → 代号（单位A…、人员1…） |
| 审计问题库 | 问题清单信息导出 | 6096 条 | 单位/人名/项目名 → 代号，可筛选/分页 |

原始 xlsx 不进入项目目录；脱敏由 `scripts/` 下脚本完成，可复核。

## 设计决策（面试可讲）

1. **严格顺序状态机 + 前置条件链**：六阶段强依赖、逐级推进——立项→审前准备→现场实施→报告编制→整改督办→项目归档；用户说「审计/继续/下一步」时按当前所处状态推进到下一待办阶段，乱序请求（没立项就要报告）被拦截并提示当前状态。每阶段进入前还校验**具名前置条件**（如「立项审批通过」「审计报告已发布」「整改闭环完成」），把审计实务的审批/发布/闭环约束做进了调度层。
2. **检索方案**：先 BM25 关键词检索验证主链路，再考虑向量检索（先验证、后优化）。
3. **阶段化检索**：知识库打阶段标签，现场只查法规、报告只查报告规范、整改只查整改要点——避免流程文档串台。
4. **人机分工**：AI 只生成草稿，放行、销号、入库都在人（审计合规红线）。
5. **防幻觉**：每个风险点必须引用知识库法规依据；检索不到就明确说「信息不足」或拒答，不臆造。
6. **架构可横向复制**：新增审计场景只加数据源注册 + 筛查规则，不动调度逻辑。
7. **类型化报告模板**：四大审计类型（经济责任/竣工决算/在建跟踪/通用）对应四套真实报告模板，任务解析输出「审计类型」字段，报告编制阶段据此路由，不改调度逻辑、只按类型换模板。
